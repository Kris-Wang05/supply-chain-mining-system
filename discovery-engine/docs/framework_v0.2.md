# 股票发现引擎框架 v0.2

基于 v0.1 草案优化。改动集中在：评分机制（加法 → 门槛+评分）、候选生命周期、
去重定义、已定价检查、闭环校准。未改动的部分（定位、发现入口、上下文调查十问）沿用 v0.1。

---

## 1. 项目定位（不变）

只负责**发现值得进一步研究的股票**。输出标准 JSON 交给 3+1 分析框架。

> 发现引擎回答"为什么现在值得研究"；3+1 框架回答"是否值得投资、什么价格值得买"。

---

## 2. v0.1 的六个结构性问题及修正

### 问题 1：加法评分让弱证据混进候选池

v0.1 四项 0–5 加总 20 分。一条"变化强度 5、认知差 5、经济影响 4、证据 1"的记录
能拿 15 分进候选池——但证据 1 分意味着它很可能是营销噪声。

**修正：两层结构。先过门槛（gate），再看分数。**

| 门槛 | 规则 |
|---|---|
| G1 证据门槛 | `evidence_score <= 2` → 最高只能进观察名单，不得进候选池 |
| G2 关系门槛 | `relationship_level == "E"` → 最高只能进观察名单 |
| G3 来源门槛 | 没有任何一级或二级来源 → 状态锁定为 `lead`，不参与评分分档 |
| G4 定价门槛 | 红旗含 `price_already_moved` → 分档自动降一档 |
| G5 稀释门槛 | 红旗含 `dilution_or_insider_selling` → 分档自动降一档，且必须在周报单独列出 |

门槛全过之后才应用分数分档（16–20 / 13–15 / 9–12 / 0–8，同 v0.1）。

### 问题 2：候选没有生命周期，会积累僵尸记录

v0.1 只有一个 `status: candidate`。三个月后候选池里全是过期事件。

**修正：状态机 + 强制复查日期。**

```text
lead ──→ contextualized ──→ verified ──→ candidate ──→ promoted   (进入 3+1)
  │             │                │            │
  └─────────────┴────────────────┴────────────┼──→ rejected  (触发 kill rule，必须记录原因)
                                              ├──→ watchlist (证据不足但事件真实)
                                              └──→ expired   (过了 review_by 无人推进)
```

- 每条记录必须有 `review_by`（复查日期）。默认：事件日期 + 90 天。
- 过了 `review_by` 没有新证据 → 自动转 `expired`。expired 可以被新事件复活（新指纹）。
- `promoted` 必须同时具备：mispricing_hypothesis、falsification_signals、下一份财报验证点。
- `rejected` 必须列出触发的 kill rule。

### 问题 3：event_type 和红旗是自由文本，无法去重和统计

**修正：受控枚举。** 完整列表见 schema 和 `models.py`。要点：

- 事件类型约 19 种，对应 v0.1 第 3 节的五大发现入口。
- 红旗 10 种固定枚举，对应 v0.1 第 8 节的误报控制规则，每条红旗直接挂钩门槛动作。
- 需要新枚举值时走规则变更流程（版本号 + 测试 + Git 提交），不允许现场造词。

### 问题 4：去重规则只说"同一事件只保留一条主记录"，没有定义"同一事件"

**修正：事件指纹。**

```text
fingerprint = sha1(ticker | event_type | counterparty | event_date[:7])
```

即：同一公司、同一事件类型、同一交易对手、同一自然月 → 视为同一事件。
旧新闻重新传播、多家媒体转载都会命中同一指纹。跨月的持续性事件（如产能爬坡）
每月最多产生一条新记录，且必须引用上一条的 fingerprint（`supersedes` 字段）。

### 问题 5：缺少"已定价检查"的强制字段

v0.1 只在风险清单里提了一句"事件已导致股价大涨：标记可能已定价"。

**修正：`price_reaction_note` 为必填字段。** 记录事件披露日前后 5 个交易日的
股价与成交量变化（来源：任何行情终端，记录数字即可）。判断标准：

- 事件窗口涨幅 > 30% 或成交量 > 10 倍均量 → 必须打 `price_already_moved` 红旗（触发 G4）。
- 无法获取行情 → 写 `[unverified]`，记录锁定为 `lead`。

### 问题 6：评分规则永远不知道自己准不准

**修正：闭环校准。** 每条到达终态（promoted / rejected / expired）的记录保留：

- `outcome_note`：最终结局（进入 3+1 后被证实/证伪、事件不了了之等）。
- 季度回看：按分档统计"promoted 且 3+1 确认值得研究"的比例。
  某一档命中率长期 < 20% → 说明该档评分虚高，收紧对应维度的评分标准（提版本号）。

## 3. 发现入口（沿用 v0.1 第 3 节）

企业关系 / 政府与监管 / 经营变化 / 资本与资产变化 / 行业变化，五类不变。
每类映射到受控 event_type 枚举，见 `models.py`。

---

## 4. 信息来源分级（沿用 v0.1 第 4 节，操作细则见 data_sources.md）

- Tier 1：监管申报、交易所公告、政府合同数据库、公司正式公告。
- Tier 2：财报电话会、投资者演示、行业协会数据、专利与认证文件。
- Tier 3：新闻、研报、社媒。**只能产生线索（lead），不能推进状态。**

每个来源必须记录：URL、发布日期、抓取日期、原文摘录（verbatim，禁止转述）、Tier。

## 6. 关系含金量分级（沿用 v0.1 第 6 节 A–E）

新增执行规则：

- 单方面宣称（`unilateral = true`）→ 关系等级在证据基础上至少降一级。
- E 级触发门槛 G2，最高观察名单。
- A/B 级必须有一级来源支撑，否则自动降为 C。

## 7. 评分与分档

四个维度 0–5 分不变：变化强度、证据可信度、经济影响、认知差与稀缺性。
`discovery_score` = 四项之和，必须等于存储值（模型校验强制）。

**分档 = min(分数档, 门槛档)：**

```text
1. 先按总分定初档：16–20 priority / 13–15 candidate_pool / 9–12 watchlist / 0–8 noise
2. 依次应用 G1–G5，取最低档
3. 每项评分必须附 rationale（评分依据），不允许只有数字
```

分档只决定研究优先级，不进入 3+1 的质量分或估值分（不变）。
